# 项目介绍

## AI 求职信息工作台（Agent-ready Recruitment Workspace）

求职不是只投递一次简历，而是同时推进多家公司、多条岗位和多轮流程。岗位信息在招聘平台，通知在邮件或聊天工具，简历又有多个版本；当测评、笔试和面试接连到来时，很容易忘记截止时间，也很难快速回答“这个岗位现在到哪一步了”“当时投的是哪份简历”“下一步要做什么”。

AI 求职信息工作台把这些分散信息放进同一个工作空间，帮助用户统一管理：

- 岗位申请
- 简历版本
- 招聘通知
- 面试、笔试与测评节点
- 截止时间和后续行动

它既是一个可以直接操作的 Web 应用，也是一份能被 AI Agent 安全读取的个人求职资料库。用户在网页中维护和确认事实，Agent 则基于这些已确认信息进行查询、总结和准备工作；通过本文介绍的 MCP 连接修改申请阶段时，最终决定仍由用户做出。

## 它解决什么问题

- 多家公司、多岗位同时推进，靠记忆或零散表格很难保持同步。
- 邮件、测评和面试通知分散，截止时间容易遗漏。
- 通用版、岗位版等简历文件混在一起，不清楚某次申请使用了哪一版。
- 岗位阶段、历史通知和下一步行动彼此割裂，无法快速了解全局。
- 每次准备面试都要重新复制 JD、简历和通知，重复整理耗费大量时间。

工作台把一次求职机会组织成一条连续记录：

```text
保存岗位 → 关联简历 → 更新投递阶段 → 导入招聘通知 → 跟进下一步行动
```

登录后，首页会集中显示整体求职进度、日历和今天需要处理的事项。

# 核心功能

以下功能按照实际求职流程介绍。主要页面入口是：首页 `/`、我的求职 `/jobs`、我的简历 `/resumes`、通知管理 `/notifications`。

## 1. 岗位管理

### 为什么需要

当岗位数量增加后，只保存一个 JD 链接并不足够。用户还需要知道公司、岗位、投递日期、当前阶段、所用简历和下一步行动，并且能够随时回看原始信息。

### 如何操作

进入“我的求职”，点击“导入岗位”：

```text
导入岗位
→ 输入岗位名称、来源链接和来源备注
→ 粘贴 JD 正文，或粘贴岗位截图
→ 生成岗位卡片
→ 核对并保存公司、岗位职责和岗位要求
```

也可以通过 Excel 批量导入已有岗位记录。保存后，用户可以：

- 在列表中查看和编辑公司、岗位、Base、行业、投递日期、来源和备注。
- 按关键词、阶段、城市和来源筛选岗位。
- 在列表或看板之间切换，并通过看板拖动岗位更新阶段。
- 为申请选择一份已经确认的简历版本。
- 进入岗位详情，维护投递渠道、下一步行动和推进备注。
- 导出岗位列表为 Excel。

### 最终得到什么

每个岗位都会形成一条可持续更新的申请记录，集中展示：

- 公司和岗位
- JD、职责、要求及原始来源
- 当前招聘阶段
- 投递时间与投递渠道
- 本次申请使用的简历
- 下一步行动、备注与历史事件

后续导入的招聘通知也会关联到这条申请，不再成为孤立的信息。

## 2. 简历管理

### 为什么需要

不同岗位往往需要不同简历版本。如果文件散落在本地，很难确认哪个版本已经核对、哪个岗位使用了哪份简历，也无法让 Agent 稳定地使用可信内容。

### 如何操作

进入“我的简历”，点击“新增简历版本”：

```text
新增简历版本
→ 填写版本名称
→ 上传文本、PDF、Word 或图片文件
→ 系统提取结构化候选人资料
→ 对照原文件检查和修正
→ 保存并确认
```

用户可以管理多份简历、添加版本说明、设定当前主简历，并在“我的求职”中为具体岗位选择所用版本。新版本不会覆盖已有版本。

只有经过用户确认的结构化简历内容，才会作为可信事实提供给 Agent。

### 最终得到什么

用户会得到一个清晰的简历版本库，并能把具体申请与具体简历关联起来。连接 Agent 后，可以基于用户确认的简历内容辅助完成：

- 面试准备
- 岗位与经历匹配分析
- 自我介绍和项目讲述思路生成
- 针对具体岗位的简历修改建议

这些分析和文本由所连接的 Agent 生成；工作台负责提供经过确认的岗位、简历和招聘进度上下文。

## 3. 招聘通知导入

### 为什么需要

笔试通知、测评通知、面试邀请和 AI 面试邀请通常以邮件或消息形式出现。手工逐项抄写时间、链接和要求既慢又容易遗漏。

### 如何操作

进入“通知管理”，点击“导入通知”：

```text
通知管理
→ 导入通知
→ 选择对应岗位
→ 粘贴邮件或通知正文
→ 可选填写邮件主题、发件人和接收时间
→ AI 解析
→ 用户核对解析结果
→ 确认通知信息
→ 写入该岗位的招聘时间线
```

当前版本由用户手动粘贴通知内容，不会连接 Gmail，也不会自动读取邮箱。

系统会从通知中提取：

- 通知类型，如笔试、测评、面试、AI 面试或截止提醒
- 固定时间、有效时间窗口或截止时间
- 线上、线下或混合形式
- 会议或测试链接、线下地点
- 要求事项
- 后续行动

解析结果不会直接成为事实。页面会先展示识别结果，只有用户点击“确认通知信息”后，内容才会保存。

### 原文证据如何保留

系统会保留通知原文，并把“要求事项”和“后续行动”作为原文摘录展示。用户可以在通知时间线中同时查看结构化结果和原始内容，核对 AI 是否理解正确，避免模型在信息缺失时自行补全。

### 最终得到什么

用户可以按岗位查看：

- 历史通知
- 待处理、已完成和已忽略的事项
- 即将到来的面试、测评和截止时间
- 通知链接、地点、要求和后续行动

这些时间信息还会进入首页日历和今日待办，减少错过关键节点的风险。

## 4. 招聘流程时间线

### 为什么需要

单一的“面试中”状态无法解释一个岗位是如何推进到当前阶段的。用户需要同时看到当前状态、过去发生过什么，以及接下来要做什么。

### 如何操作

用户可以从两个入口查看流程：

- 在“我的求职”中打开岗位详情，查看当前阶段、推进备注和已有记录。
- 在“通知管理”中打开对应机会，查看按待处理、已完成和已忽略分组的通知时间线。

例如，一条申请可能形成这样的记录：

```text
腾讯 · 技术产品商务培训生
已投递
↓
在线测评
↓
一面邀请
↓
待准备
```

用户可以在岗位详情中手动更新阶段，在通知详情中修改通知、调整关联岗位，或将事项标记为已完成、已忽略。

### 最终得到什么

每个岗位都有独立的招聘历史，用户可以看到时间节点、通知来源与原文、当前阶段和下一步行动。首页再把所有岗位中的关键节点汇总成日历和今日事项，方便安排求职节奏。

# AI Agent 联动

## Web 应用和 Agent 如何协同

Web 应用负责保存、展示和确认求职事实；Agent 负责读取这些事实，并按用户指令进行整理、分析或提出修改建议。下面的协作流程特指本文介绍的 MCP 连接方式。

```text
用户在 Web 中维护岗位、简历和通知
                ↓
       Agent 读取已授权信息
                ↓
     Agent 查询、总结、分析或提出建议
                ↓
   涉及数据修改时回到 Web 由用户确认
```

有两种使用方式：

1. **复制上下文，无需连接。** 打开某个岗位详情，在“准备 AI 上下文”中复制 AI Context、JSON 或完整 Prompt，再粘贴给 ChatGPT、Codex 或其他 Agent。上下文会整理岗位、已确认简历、申请状态和相关通知。
2. **连接自己的 Agent。** 使用工作台提供的 Agent 连接地址，让支持 MCP 的客户端按需读取申请、简历、事件和截止时间。

无论使用哪种方式，工作台都只把已保存的数据当作上下文；对于结构化简历，只有用户确认后的版本才会提供给 Agent。

## Agent 可以完成什么任务

### 信息查询

用户可以问：

> 帮我总结目前所有投递情况。

Agent 可以读取岗位列表，按公司和当前阶段整理已投递岗位、最近进展与下一步行动。

也可以问：

> 帮我查看最近有哪些岗位需要处理。

Agent 可以读取今天的招聘事件和未来一段时间的截止事项，整理即将截止的测评、最近的面试邀请和待处理任务。

### 面试准备

用户可以问：

> 帮我准备腾讯技术产品商务培训生一面。

Agent 可以读取该申请的岗位信息、JD、当前阶段、历史通知，以及与申请关联的已确认简历，再生成自我介绍思路、高频问题和项目准备方向。

### 状态同步

用户可以说：

> 长鑫已经通知我 AI 面试，把状态更新一下。

对于通过 MCP 发起的申请阶段更新，Agent 不会直接改写记录，而是创建一条待确认建议：

```text
Agent 提出修改建议
→ 网站生成“待确认事项”
→ 用户查看具体变化和建议来源
→ 用户确认或拒绝
→ 确认后系统更新岗位状态
```

这个 Human-in-the-loop 流程避免 Agent 因理解错误而改动重要求职信息。Agent 只能访问当前 Token 所属用户的数据；关闭或已拒绝的申请也不能通过该建议流程继续推进。

## Agent 当前可用能力

连接成功后，Agent 可以：

- 查询申请列表，并按公司或阶段筛选。
- 查询某个申请的 JD、状态、备注和完整事件时间线。
- 读取指定的、已经由用户确认的简历版本。
- 查询今天的招聘事件。
- 查询未来 1 至 31 天内的截止事项。
- 为申请阶段变更创建待确认建议。
- 在用户已确认后，执行保存好的阶段变更或招聘事件变更。

# Agent 连接配置

## 如何连接自己的 AI Agent

### 连接前准备

需要一个支持远程 MCP（Streamable HTTP）并允许配置自定义请求头的 Agent 客户端。

先登录工作台，打开：

```text
账号 → 设置 → Agent 接入
```

填写 Token 名称并点击“生成 Token”。Token 明文只展示一次，请立即复制并保存在受信任的客户端中；如果怀疑泄漏，可以在同一页面撤销。

### 连接步骤

1. 打开 Agent 客户端的设置。
2. 添加一个远程 MCP Server。
3. 填写 Server URL 和认证请求头。
4. 保存配置并完成连接。

当前项目配置中的生产地址为：

```text
https://project-iry1g.vercel.app/api/mcp
```

本地运行时使用：

```text
http://localhost:3000/api/mcp
```

认证请求头为：

```text
Authorization: Bearer <YOUR_API_TOKEN>
```

不同客户端的配置字段名称可能不同，但等价配置如下：

```json
{
  "url": "https://project-iry1g.vercel.app/api/mcp",
  "headers": {
    "Authorization": "Bearer <YOUR_API_TOKEN>"
  }
}
```

如果项目部署到其他域名，Server URL 应使用该环境的 `APP_URL`，并在末尾加上 `/api/mcp`。

### 连接后如何验证

可以先让 Agent 执行一个只读请求，例如：

> 列出我的岗位申请，并告诉我每个岗位当前处于什么阶段。

如果 Agent 能返回当前账户中的申请数据，说明连接和 Token 均已生效。之后可以继续查询简历、招聘事件和截止时间，或让 Agent 创建一条需要在网页中确认的阶段更新建议。

# 当前使用边界

- 不会自动登录招聘网站或代替用户投递岗位。
- 不会自动读取邮箱；招聘通知需要用户手动粘贴。
- 不会把未经确认的简历解析结果提供给 Agent 当作事实。
- 通过 MCP 提出的申请阶段修改必须先由用户确认，不能静默生效。
- Agent 生成的面试准备、自我介绍和匹配分析属于辅助内容，仍需用户检查和判断。

# 技术实现

这是一个基于 Next.js 和 React 的 Web 应用，使用 Prisma 管理数据访问；生产环境使用 PostgreSQL，本地开发可使用仓库中的 SQLite 配置。简历文件可接入 Vercel Blob，AI 解析使用可配置的 OpenAI-compatible 服务。

项目通过 Streamable HTTP 提供 MCP Server，并用用户级 API Token 隔离数据。MCP 中的申请阶段修改采用 Human-in-the-loop Proposal workflow：Agent 先生成待确认建议，用户确认后，再由受控的服务端流程执行。

项目还提供 Bearer Token 保护的 Agent API 和可配置 Webhook，供 n8n、脚本或其他自动化工作流接入。Agent API 包含可直接写入岗位、申请阶段、事件和外部生成结果的高级接口，不等同于上面的 MCP 确认流程；只应把 Token 交给受信任的自动化服务，并通过站内 Agent 运行记录审查结果。
